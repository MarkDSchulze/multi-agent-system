MULTI-AGENT BUSINESS OPERATIONS SYSTEM
Design Notes

Author: Mark Schulze

OVERVIEW

This solution uses a multi-agent architecture to automate business operations related to quoting, inventory management, supplier coordination, financial validation, and order fulfillment.

The system was designed to separate responsibilities across specialized agents while maintaining clear business controls, inventory accuracy, and financial accountability.

The architecture follows an orchestration pattern where a central orchestrator coordinates specialized worker agents responsible for quoting, inventory management, and order processing.

ARCHITECTURE

The solution consists of three primary agents:

1. Quote Agent
2. Inventory Management Agent
3. Ordering Agent

The system also includes an orchestrator function (call_multi_agent_system) that coordinates communication and workflow execution between agents.

Orchestrator Responsibilities

- Receive customer requests
- Coordinate quote generation
- Coordinate inventory validation
- Route information between agents
- Manage end-to-end workflow execution
- Return final customer responses

Quote Agent Responsibilities

- Search historical quote records
- Reference prior customer requests and quote explanations
- Estimate pricing for requested products
- Identify supported and unsupported products
- Use catalog pricing and discount logic
- Provide preliminary pricing information

Inventory Management Agent Responsibilities

- Check current inventory levels
- Evaluate inventory availability
- Calculate supplier lead times
- Check cash availability
- Generate company financial reports
- Support order validation decisions

Ordering Agent Responsibilities

- Process complete customer requests
- Extract products, quantities, request dates, and delivery dates
- Validate inventory availability
- Validate supplier lead times
- Validate cash availability
- Create replenishment transactions when necessary
- Create sales transactions
- Finalize customer orders
- Return fulfilled or rejected order decisions

BUSINESS RULES

Inventory Validation

Inventory is evaluated using transaction history rather than static inventory values.

Available inventory is calculated using:

Stock Orders – Sales = Available Inventory

Inventory checks are performed using the required delivery date to account for previously scheduled replenishment and fulfillment transactions.

Supplier Validation

Supplier lead times are determined by requested quantity:

- 10 units or fewer: Same day
- 11–100 units: 1 day
- 101–1000 units: 4 days
- More than 1000 units: 7 days

Orders are automatically rejected when required replenishment inventory cannot arrive before the customer delivery deadline.

Financial Validation

Before creating replenishment orders, the system validates that sufficient cash exists to cover all required inventory purchases.

Orders are rejected when replenishment costs exceed available cash.

This prevents the company from creating inventory obligations that cannot be funded.

PRODUCT RESOLUTION

Customers frequently use terminology that differs from catalog product names.

The solution implements normalization and alias resolution logic to map customer language to supported catalog products.

Examples:

- "A4 printer paper" → "A4 paper"
- "standard printer paper" → "Standard copy paper"
- "colorful cardstock" → "Cardstock"
- "A4 matte paper" → "Matte paper"

This improves order accuracy and reduces transaction failures caused by inconsistent terminology.

DISCOUNT LOGIC

Bulk discounts are applied using deterministic quantity thresholds.

Discount Tiers

- 500+ units: 5%
- 1000+ units: 10%
- 5000+ units: 12%
- 10000+ units: 15%

This ensures consistent and explainable quote and fulfillment pricing.

ORDER FULFILLMENT STRATEGY

Orders are processed as complete transactions.

The solution does not partially fulfill customer orders.

If any product is unsupported, unavailable within the required timeline, or unaffordable due to financial constraints, the entire order is rejected.

This approach preserves business consistency and prevents incomplete customer deliveries.

KEY DESIGN DECISIONS

1. Separate quote generation from fulfillment decision-making.

2. Use specialized agents with clearly defined responsibilities.

3. Validate inventory using delivery dates rather than request dates.

4. Use transaction history as the inventory source of truth.

5. Reject unsupported products rather than attempting substitutions.

6. Reject incomplete orders rather than allowing partial fulfillment.

7. Apply deterministic pricing and discount logic for consistency and transparency.

8. Maintain financial controls before creating replenishment orders.

9. Use supplier lead-time validation to ensure realistic delivery commitments.

10. Preserve transactional integrity through structured sales and replenishment records.

EVALUATION RESULTS

The solution was evaluated using the complete set of requests provided in quote_requests_sample.csv.

The evaluation demonstrated that:

- Multiple customer requests were successfully fulfilled.
- Inventory replenishment transactions were created when stock shortages occurred.
- Cash balances changed during simulation as inventory purchases and sales transactions were processed.
- Supplier lead-time validation prevented unrealistic delivery commitments.
- Multiple customer requests were rejected when inventory or supplier constraints could not be satisfied.
- The system consistently enforced inventory, supplier, and financial controls before fulfilling orders.
